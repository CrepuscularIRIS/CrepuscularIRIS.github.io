长上下文语言模型面临一个根本性的工程矛盾：自注意力的二次复杂度意味着，每将上下文窗口翻倍，计算量就要翻四倍。如果用标准注意力处理 1M token，这个模型在经济上根本无法部署——光是推理成本就足以排除任何实际应用场景。

Kimi K2.5 绕过了这个问题，它叠加了三项架构决策，每一项都独立降低了注意力复杂度负担，并将它们与测试时计算扩展研究中的推理方法相结合。最终成果：一个模型在 1M token 上处理的推理成本，低于 GPT-4o 在 128K 上的成本，同时在长文档基准测试中表现更优。

本文从技术层面拆解每一个组件。

## 二次复杂度问题的具体数字

对长度为 $n$ 的序列进行标准自注意力，需要 $O(n^2)$ 的内存和计算量来处理注意力矩阵。在 128K token 时，这已经代价不菲——每层大约需要 160 亿次注意力操作。在 1M token 时，同样计算每层需要 1 万亿次操作。这是上下文长度增加 8 倍，计算量增加 64 倍。

没有任何硬件扩展能让这在生产推理中可行。架构选择必须改变。

Kimi K2.5 组合的三项技术——稀疏注意力、动态深度路由和改进的位置编码——每一项都针对这个问题的不同部分。

## 稀疏注意力：不是所有 token 都需要attend to所有其他token

稀疏注意力的核心观察是：对于大多数实际的长上下文任务，任何给定 token 只需要attend to上下文的一小部分。一份法律文档中间的一句话，不需要直接attend to其他每个段落的每个词——它需要局部上下文（相邻句子）和全局锚点（关键定义、标题、命名实体）。

Kimi K2.5 采用的是**滑动窗口混合（Mixture of Sliding Windows）**方法：不是单一固定窗口大小，而是根据输入内容，将每个注意力头路由到多个滑动窗口尺度中的一个。

```python
class MixtureOfSlidingAttention(nn.Module):
    def __init__(self, d_model: int, num_heads: int, window_sizes: list[int]):
        super().__init__()
        self.heads_per_window = num_heads // len(window_sizes)
        self.windows = nn.ModuleList([
            SlidingWindowAttention(
                d_model=d_model,
                num_heads=self.heads_per_window,
                window_size=w,
            )
            for w in window_sizes
        ])
        # Router: 预测这个 token 位置适合哪个窗口尺度
        self.router = nn.Linear(d_model, len(window_sizes))

    def forward(self, x: torch.Tensor, position_ids: torch.Tensor) -> torch.Tensor:
        # 计算每个 token 的路由权重
        routing_logits = self.router(x)          # [B, T, num_windows]
        routing_weights = torch.softmax(routing_logits, dim=-1)

        # 各窗口尺度输出的加权和
        outputs = []
        for i, window_attn in enumerate(self.windows):
            out = window_attn(x, position_ids)   # [B, T, d_model]
            outputs.append(out * routing_weights[..., i:i+1])

        return sum(outputs)
```

关键洞察：代码往往具有高局部密度（括号匹配、变量作用域），适合窄窗口；叙事文本适合段落级（中）窗口；文档级推理任务（法律、科学）需要更宽的窗口来桥接远处引用。

通过将窗口大小变为一个柔软的、可学习的决策而非固定超参数，模型将注意力带宽分配到真正需要的地方。

复杂度降低效果显著。在 1M token 上使用 4096 token 滑动窗口，需要 $O(n \cdot w)$ 的注意力操作（$w = 4096$），相比全注意力的 $O(n^2)$ 大幅减少。在 1M token 上，注意力计算减少约 250 倍。

## 动态深度路由：让计算匹配任务复杂度

第二项架构创新针对另一个低效问题：均匀深度。在标准的 32 层 Transformer 中，每个输入都经过全部 32 层，而不管任务是否真的需要这种处理深度。简单的事实查询不需要和多步数学推理一样的处理深度。

Kimi K2.5 实现了**动态深度路由**：一个轻量级门控机制，逐 token、逐层决定是执行完整 Transformer 块还是跳过它。实际效果：简单 token 提前退出网络，将计算集中在真正需要深度处理的位置上。

| 任务类型 | 有效层利用率 | 相对推理成本 |
|-----------|------------|------------|
| 简单事实检索 | ~40% | 0.6× |
| 代码补全 | ~75% | 0.85× |
| 复杂多步推理 | 100% + 反思 | 2–4× |
| 长文档摘要 | ~60% | 0.75× |

表格中的数字来自 K2.5 技术报告的近似值——实际路由决策与内容相关，以 token 粒度变化。在真实 workloads 混合下，相比始终执行所有层，总体推理计算量减少约 30%。

这在结构上类似于 MoE（混合专家）路由，但应用于深度而非宽度。模型没有增加参数——它只是决定对给定 token 实际使用多少现有参数。

## 位置编码：在训练长度之外做外推

长上下文模型面临一个位置编码问题：即使架构能高效处理 1M token，在 128K 序列上训练的位置编码并不能可靠地泛化到更长的位置。模型在训练时从未见过位置 500,000。

标准修复方案——在更长序列上训练——代价很高。Kimi K2.5 转而使用旋转位置嵌入（RoPE）上的 **NTK-aware 插值**，允许模型以最小的质量退化将上下文长度显著扩展到训练范围之外。

数学基础：标准 RoPE 在维度 $2i$ 中将位置 $m$ 编码为：

$$\theta_{m,i} = m \cdot \theta_{base}^{-2i/d}$$

当位置 $m$ 超过训练长度 $L_{train}$ 时，旋转角度变得 out-of-distribution。NTK-aware scaling 对基频应用一个学习到的插值因子 $\alpha$：

$$\theta_{m,i} = m \cdot \left(\alpha \cdot \theta_{base}\right)^{-2i/d}$$

缩放因子 $\alpha$ 的设置原则是：使位置编码中最高频维度不会在扩展上下文窗口内饱和。低频维度（编码粗粒度位置结构）基本保持不变；高频维度（编码细粒度局部位置）被抑制。

结果是：模型可以"读取"它从未训练过的位置，而不会产生灾难性混淆——代价是在训练长度之外非常细粒度的位置区分上精度略有下降。

## 长上下文实际上意味着什么（以及不意味着什么）

一个常见误解：能处理 1M token 的模型，也能可靠地*记住*该上下文中任意距离的任何内容。

这在重要方面是错误的。基于注意力的 Transformer 是处理器，不是记忆。在生成 token $t$ 时，模型attend to所有先前的 token——但来自 token $1$ 的信号在经过网络的每一层时已经被逐步转换和压缩。来自上下文非常早期的信息在到达生成步骤时，不会具有与附近上下文相同的信息保真度。

实际含义：长上下文模型在需要*查找和综合*远处位置信息的任务上表现出色（例如，"在这份文档中找到 X 的所有提及并总结它们的关系"）。在需要*逐字回忆*超长上下文开头精确细节的任务上表现较差。

Kimi K2.5 通过在预处理阶段进行**分层 key 提取**来解决这个问题：在主前向传播之前，一个轻量级模块扫描输入，在语义重要位置（关键定义、章节标题、实体引入）插入显式"锚点"token。这些锚点在主传播期间获得人为提升的注意力权重，为模型提供了一个可寻址的索引来进入长上下文。

## 基准测试结果放在具体场景中

在 LongBench-v2 上，K2.5 报告：

| 模型 | 最大上下文 | LongBench-v2 得分 | 相对推理成本 |
|------|-----------|-----------------|------------|
| GPT-4o | 128K | 62.3 | 1.0× |
| Claude 3.5 Sonnet | 200K | 64.1 | 1.2× |
| Kimi K2.5 | 1M | 67.8 | 0.7× |
| Gemini 1.5 Pro | 2M | 65.2 | 1.5× |

0.7× 推理成本这个数字值得仔细审视。这是*每处理一个 token* 的相对成本，而 1M 上下文意味着满上下文 K2.5 查询的绝对成本仍然远高于典型 128K GPT-4o 查询。效率优势在需要长上下文的 workloads 上最为重要——如果你的中位查询是 10K token，K2.5 的架构优化帮助不大。

效率优势真正发挥的场景：文档级分析任务（法律、科学、金融）、代码库级推理（将整个大型代码仓库作为一个整体理解）、多文档综合。对于这些任务，K2.5 可以单次处理完整上下文，而不需要分块或检索增强。

## 工程启示

**何时用 K2.5 vs. RAG**：对于可以预计算嵌入的文档集合且查询相对狭窄的情况，使用短上下文模型的检索增强生成通常更便宜。当查询需要综合多个难以独立检索的远处位置的信息，或者多步检索的延迟成本不可接受时，K2.5 的长上下文才变得划算。

**在长上下文下 prompt 结构更重要**：分层锚点机制在 prompt 本身有结构时效果更好——清晰的章节标题、文档早期明确的关键词定义。无结构的文字墙会以一种有结构文档不会的方式给注意力模式带来压力。

**对研究应用**：1M token 上下文开辟了真正全新的研究工作流。在单个上下文窗口中处理完整的会议论文集、整个代码库或多年实验日志，改变了一类综合问题的可解性边界。瓶颈从"模型能处理吗？"转移到"我如何正确地表述问题？"

## 接下来会怎样

K2.5 中的三项技术——稀疏注意力、动态深度、扩展位置编码——每一项都已被独立理解。真正的贡献是它们的组合，以及让它们在生产规模上可靠协同工作的工程工作。

下一个前沿是：将长上下文注意力与显式外部记忆相结合的架构。当前的长上下文模型仍有软限制：注意力模式在 1M token 上下文远端变得越来越嘈杂，没有位置编码工程能完全修复这个问题。将注意力用于局部/中范围上下文、将检索用于全局/远处引用的混合架构，是突破当前实际限制最有希望的方向。

关于长上下文评估的研究问题也尚未被充分探索。LongBench-v2 是一个合理的基准，但它没有完全捕捉实践中最重要的失败模式——模型看起来回答正确但已悄悄丢弃了早期上下文关键信息的任务。构建能够暴露这些失败模式的评估套件，与构建更好的架构同样重要。
