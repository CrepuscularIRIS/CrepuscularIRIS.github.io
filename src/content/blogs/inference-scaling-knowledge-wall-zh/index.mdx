推理时 Scaling——让模型在每次查询时思考更长时间，无论是扩展思维链、采样多次尝试，还是运行树搜索——是 2024 至 2026 年间最核心的能力叙事。OpenAI 的 o1 演示了它，DeepSeek-R1 将其产品化，Claude Opus 4.6 将其暴露为可调的 `effort` 参数，GPT-5.4 将其定价为"推理分钟"。主线逻辑一致：付更多推理时算力，在数学、代码和竞赛类题目上获得明显更好的答案。

而同一叙事较少被听到的，是它在哪些情况下失效。2026年4月越来越多的工作指向一类特定任务：推理时 Scaling 不仅会趋于平稳，还可能让模型*变差*。这类任务是知识密集型问题，尤其是那些需要模型在训练时可能没有干净编码的事实的问题。

这件事很关键，因为我们想让 AI 代理做的很多事——研究助手、客服机器人、合规审查员、任何引用真实来源的工具——恰恰都是知识密集型的。如果"让模型想更久"的故事在那里失效，代理设计者需要一个比当前"更多推理 token = 更好"这种民间智慧更细致的图景。

## 2026年4月的证据说了什么

两项工作值得放在一起来看。

第一篇是发表在 OpenReview 上的论文，标题为"推理模型的测试时 Scaling 对知识密集型任务尚无效果"。研究评估了 14 个推理模型在知识密集型基准测试（包括 SimpleQA 和 FRAMES）上的表现。结果：扩展思维预算（更多回答 token、更深的思维链）并不能一致地提高准确率。在几种配置上，更长的推理甚至*增加了*幻觉率。模型有了更多思考空间，用那个空间来构建更自信的错误答案。

第二篇是今年早些时候的一篇 arXiv 论文，"动态推理的代价：从 AI 基础设施角度解读 AI 代理与测试时 Scaling"，研究了不同推理时 Scaling 旋钮下代理的 compute-accuracy 曲线——反思深度、并行采样、少样本数量。其标题不是关于失败模式，而是关于收益递减。准确率随算力增长，但斜率快速平坦，延迟方差扩大。在严格的生产 SLO 下，边际推理 token 的价值往往低于边际检索文档。

这两项发现指向同一个底层结构：推理时 Scaling 是对解空间的*搜索*，而搜索只在正确答案能从模型已有知识中达到时才有帮助。对于数学和代码，解空间是程序性的——模型从已记忆的算子组合步骤。更长的搜索给了它更多尝试来组合正确序列的机会。对于知识，解空间是检索——答案要么在权重里，要么不在。思考更久并不会把一个不在权重里的事实放进去。

## 为什么想更久反而可能更糟

反直觉的部分不是 Scaling 在知识任务上趋于平稳——这几乎不言自明——而是它有时会*逆转*。值得理解的机制：

当推理模型被提示一个它不确切知道的事实时，短思维链基线通常会浮现一个不确定性标记："我不确定，但我觉得 X。"长思维链后训练改变了这一点。模型因产生结构化推理轨迹而获得奖励。它隐含地学会用支持性脚手架装饰弱答案——编造的引用、听起来合理的推导、虚构的中间结论。推理链自洽但属于幻觉。

这不是任何单一模型的 bug。这是训练信号的可预测后果。如果"更多推理 token"作为一种策略被奖励，模型就会找到方法来填充那些 token，即使它没有真正的信号来推理。对于数学问题，这没关系——正确答案可验证，所以填充物会被奖励函数剪枝。对于知识问题，这很糟糕——训练中没有"模型是否编造了引用"的验证器，所以填充物会持续存在。

一个有用的思考方式：幻觉率不会爆炸，但会改变*性质*。更短、更不确定的含糊措辞变成了更长、更自信的虚构。净准确率可能持平；但信任损失的幅度大于准确率差异所暗示的，因为自信但错误对于大多数下游使用来说是更糟糕的失败模式。

## 什么在知识任务上真正有效

替代方案并不神秘。只是需要承认，推理算力在检索问题上花的不是地方。

**先检索，再推理。** 最干净的范式，大多数生产系统已经在用。将问题分解为一个或多个检索调用，然后让模型对检索到的文本（而非记忆）进行推理。算力旋钮从"更多推理 token"转向"更好的检索"。"动态推理的代价"这项工作描述了准确率-成本权衡如何随推理预算增长而平坦——结合上述 OpenReview 结果——意味着在知识受限任务上，边际检索算力往往优于边际推理算子。确切的交叉点高度依赖于任务、检索器和模型。

**对生成内容使用结构化验证器。** 当模型输出一个引用、日期、报价、API 名称时——在返回前对其进行编程验证。一些代理现在运行后生成验证通道，每个具体声明都会查证。这不能捕获一切，但能捕获那些尴尬的部分（编造的论文标题、错误的作者、死链），而这些正是大多数用户评判代理的标准。

**置信度感知解码。** 不要让模型用推理风格的填充物来padding答案，而是暴露校准后的不确定性。"我对这个没有 confident 的答案"是比自信的虚构更好的失败模式。一些团队正在尝试训练信号，在模型内部置信度低时惩罚长思维链——一个有前景的方向，但尚未解决。

**按任务选择正确模式。** 代理设计中新兴的最佳实践不是全局拧 `effort` 旋钮，而是按子任务路由。数学类子任务获得高推理预算。检索类子任务获得高检索预算和低推理预算。代码子任务处于中间位置。尊重这种区别的系统会在值得的地方花费算力，在不值得的地方节省算力。

## 路由逻辑示意

一个最小化路由器大概长这样。这是伪代码——不要当作可直接生产的代码——但它捕捉到了形状。

```python
def route(task: Task) -> ExecutionPlan:
    """根据任务的主要失败风险将其路由到执行模式。"""
    kind = classify(task)  # 廉价分类器：knowledge / procedural / mixed

    if kind == 'knowledge':
        return ExecutionPlan(
            reasoning_budget='low',         # 短 CoT
            retrieval_budget='high',        # 多次查询，新鲜来源
            verification='strict',          # 每个具体声明都后检
        )
    if kind == 'procedural':                # 数学、代码、推导
        return ExecutionPlan(
            reasoning_budget='high',        # 让它思考
            retrieval_budget='low',
            verification='self-consistency',
        )
    # Mixed
    return ExecutionPlan(
        reasoning_budget='medium',
        retrieval_budget='medium',
        verification='strict-on-claims',
    )
```

关键观察：`reasoning_budget` 和 `retrieval_budget` 是两个独立的旋钮。过去两年推理时 Scaling 的工作隐含地将它们合并为一个——"更多算力"意味着"更多推理 token"——而这种混淆正是产生知识天花板失败模式的原因。将它们分开是第一步回头。

## 对解读基准测试的启示

如果你在看 SWE-bench Pro 分数、GPQA 分数、MATH 分数——你看的都是程序性基准。推理时 Scaling 在那里的结果可以推广到类似的程序性任务，仅此而已。当供应商宣布"我们的新高努力模式在 SWE-bench Pro 上达到 64%"，这个数字告诉你的是代码中程序性子任务的情况，而不是模型是否会在你的企业研究助手中断言一个错误的季度收入数字。

真正预测知识任务行为表现的基准——对抗性提示下的 TriviaQA、FreshQA、领域特定事实 QA——在供应商发布文章中始终缺席。这个缺席不是中性的。它反映了供应商希望被评判的能力，而知识接地不是其中之一。

2026 年的一个实际做法是在迁移现有知识接地的代理之前，对每个新模型运行一个小型的内部知识 QA 评估。一组需要从*你的*领域检索的五十个问题，带有标准答案。在这个上评分模型，而非在标题推理数字上。两个排名经常不一致。

## 更宏观的图景

推理时 Scaling 是真实的。它改变了模型在程序性问题上能做什么，也将改变代理在长期计划上能做什么。故事不是假的——只是比营销暗示的要窄。

2026 年正在澄清的是：推理算力和检索算力是两种不同的资源，而*测试时*只在特定任务类的奖励信号明确定义时才有价值扩展。对于数学和代码，它是有价值的。对于知识，它不是——至少现在还不是。直到训练制度明确奖励知识任务上的接地、不确定性校准、检索整合的长思维链，更长的思考将继续产生更自信的幻觉——而我们想要的是更少、更短的幻觉。

绕过去的方法已在生产中。先将知识问题路由到检索和短推理。将程序性问题路由到长推理和廉价检索。在奖励信号所在的地方花费算力。这不是一个华丽的研究方向，但它是真正让代理在用户关心的任务上表现正确的方向。
