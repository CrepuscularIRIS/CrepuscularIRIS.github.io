2026 年 4 月前两周做出的架构决策，比大多数季度加起来都多。四个进展值得单独拎出来说——它们改变的是部署约束，而不是功能列表。每个进展对应 agent 技术栈的不同层次：协议层、框架层、评测层、运行时层。综合起来，它们代表行业最清晰的表态：**瓶颈已从模型能力转移到部署基础设施**。

## MCP 的协议层重构

Model Context Protocol 转向无状态 HTTP 传输（SEP-1442）——这在 changelog 里看起来很无聊，实际上重构了 agent 工具的部署方式。核心动作：用标准 HTTP 请求-响应替代持久 SSE 连接，将会话状态编码为每次请求中的恢复令牌。

### 为什么 SSE 曾是瓶颈

旧架构要求每个 agent 维护到所有可能调用的工具服务器的持久 SSE 连接。以一个连接了 8 个工具服务器（GitHub、数据库、搜索、CI、监控、文件系统、终端、浏览器）的编程 agent 为例，每个 agent 实例需要 8 条持久连接。扩展到 100 个并发 agent，工具基础设施要承受 800 条持久连接。

持久连接破坏三种现代后端理所当然的部署模式：

1. **水平扩展。** 标准负载均衡器跨副本分发请求。持久连接制造粘性会话，将 agent 实例绑定到特定工具服务器副本——副本故障会导致会话状态丢失。

2. **Serverless 部署。** Lambda、Cloud Run 等平台支持缩容到零、按调用计费。持久连接阻止缩容到零，将工具服务器变成常驻基础设施。

3. **连接多路复用。** HTTP/2 和 HTTP/3 在共享连接上多路复用请求。SSE 连接是单向流，无法与工具调用请求共享。

### 无状态传输解锁了什么

SEP-1442 之后，MCP 工具服务器可以像普通 REST API 一样部署。每个工具调用是独立 HTTP 请求，携带编码会话上下文的恢复令牌。工具服务器校验令牌、处理请求、返回带有更新令牌的结果。两次请求之间，服务器端不保留任何连接状态。

实际后果：MCP 工具服务器可以挂在标准负载均衡器后面、按请求量水平扩展、部署在 serverless 平台、使用标准 HTTP 缓存和 CDN 基础设施。运维复杂度从"自定义 WebSocket 基础设施"降到"标准 Web 服务"。

### SEP-1686 Tasks 原语：异步工具调用

与无状态传输配套，SEP-1686 引入了 Tasks 原语，处理长时间运行的工具调用。这个模式对用过 webhook API 的人来说很熟悉：不再在测试套件运行 3 分钟期间阻塞连接，工具服务器立即返回一个任务句柄。Agent 轮询该句柄（或接收回调），结果就绪时获取。

```
Agent → 工具服务器: POST /tools/run-tests
工具服务器 → Agent: 202 Accepted, task_id: "abc123"

[... 3 分钟后 ...]

Agent → 工具服务器: GET /tasks/abc123
工具服务器 → Agent: 200 OK, status: "completed", result: { ... }
```

这是每个生产 API 已经在用的异步任务模式。MCP 之前缺少这一环，意味着 agent 要么在长时间运行的工具调用中阻塞（浪费推理算力），要么工具服务器伪造同步响应（返回不完整结果）。

对于团队用多个 agent 对抗共享工具服务器的场景，**SEP-1442 + SEP-1686 是解锁水平扩展的那次更新**。

## Microsoft Agent Framework 1.0 正式发布

Microsoft 在 4 月初发布了 Agent Framework 1.0 GA，将之前两个独立项目——Semantic Kernel（企业级 LLM 应用 SDK）和 AutoGen（多 agent 系统研究框架）——合并为单一 SDK，拥有统一的 agent 抽象。

### 合并的意义

Semantic Kernel / AutoGen 的分叉映射了一种常见的组织分野：Semantic Kernel 来自 Azure AI 团队，面向需要结构化、可预测 LLM 集成的企业开发者。AutoGen 来自 Microsoft Research，面向需要灵活、实验性多 agent 系统的研究人员。两套框架 API 不同、运行时模型不同、目标用户不同。

合并承认了一件事：**"企业 LLM 集成"与"多 agent 系统"之间的鸿沟已经弥合**。生产部署现在普遍涉及跨工具协调的多个 agent——正是 AutoGen 设计的模式，但同时需要 Semantic Kernel 构建时考虑到的可靠性保障。

### 原生 MCP + A2A 支持

最重大的架构新增：原生 MCP 支持，用于工具发现。不再是每个 agent 框架各自实现自己的工具集成层——Agent Framework 1.0 通过 MCP 标准协议发现工具。这意味着为 Claude Code、Gemini CLI 或任何其他 MCP 客户端构建的工具，无需适配代码，立即对 Microsoft 框架下的 agent 可用。

Agent-to-Agent（A2A）协议支持计划在数周内发布。A2A 解决了一个将多 agent 部署锁死在单一框架内的互操作性问题：一个用 LangGraph 构建的 agent 可以发现并与用 Microsoft 框架构建的 agent 通信——前提是两者都实现了 A2A。能力广告机制让 agent 广播自己能做什么，实现了动态组合而非硬编码编排图。

### DevUI：生产级调试

发布内置 DevUI——基于浏览器的调试器，实时可视化 agent 消息流。可以追踪请求在多个 agent 间的流转、检查工具调用参数和响应、重放失败交互、定位任务在哪一环脱轨。

这就是框架面向生产团队而非原型构建者的信号。多 agent 系统最难搞的运维问题是诊断 agent 链中的失败——链中每个 agent 的决策都依赖前一个 agent 的输出。DevUI 让完整消息流变得可见。

## Benchmark 变异量化了 SWE-bench 的差距

Agent 评测领域最近的工作引入了"基准变异"——一种将 SWE-bench 中干净、规范的 GitHub issue 转化为嘈杂、模糊查询的技术，更接近真实世界 bug 报告。结果：多个测试配置中，**报告性能高估超过 50%**。

### SWE-bench 过度规格化的两种形式

标准 SWE-bench 给 agent 提供了真实软件开发中不存在的两种强监督：

**清晰的 issue 规格。** 每个 SWE-bench 任务以精确描述 bug 的 GitHub issue 开头，往往包含具体失败行为、预期行为，有时甚至有具体代码位置。真实的 bug 报告通常这样写："导出坏了"或"大输入时有时崩溃"。

**测试预言机。** 每个任务包含一套测试套件，作为二元通过/失败评估器。agent 知道：测试通过意味着修复正确。真实开发中，测试套件可能不完整，失败行为可能没有被现有测试覆盖，开发者必须自行编写新测试来验证修复。

### 变异做了什么

基准变异系统性地降低这些监督质量：

- **Issue 描述变异：** 用模糊描述替换具体错误信息。移除代码位置。添加无关上下文（无关系统的堆栈跟踪、用户对根因的猜测）。
- **测试预言机变异：** 移除失败测试，只留下回归套件。Agent 现在必须对照未陈述的行为期望验证自己的修复。

两种变异同时应用后，前沿模型在 SWE-bench 上的性能从报告的 **45-60%** 区间跌至 **20-30%**。这个差距衡量了：基准性能中有多少来自真正解决工程问题，有多少来自跟随被交付给 agent 的规格。

### 轨迹分析

相关工作正在将评估从二元通过/失败转向轨迹分析——不仅要问"agent 是否产生了正确的补丁？"，还要问"agent 推理是否高效？"

轨迹指标包括：
- **工具调用次数。** Agent 执行了多少次文件读取、搜索和编辑？高效的 agent 收敛更快。
- **死路检测。** Agent 追求一个假设、意识到错了、回退的频率有多高？频繁回退意味着初始推理质量差。
- **回退率。** Agent 诉诸通用策略（读遍目录中每个文件、每次修改后运行完整测试套件）的频率，与针对性调查的频率对比。

这些指标在运营上有实际意义：**token 成本随轨迹长度线性增长**。一个用 15 次工具调用解决 bug 的 agent，比用 75 次解决同一 bug 的 agent 便宜 5 倍，哪怕两者都产生了正确的补丁。在生产环境中 agent 每天处理数百个任务，轨迹效率决定整个系统是否经济上可行。

如果你的团队正在用 SWE-bench 数字校准对编程 agent 的信任度，把那个数字对折估算真实任务的表现。然后评估 agent 的推理轨迹是否高效——因为低效轨迹上的 token 成本，才是真实的生产支出所在。

## Gemini CLI 的动态沙箱

Google 在 Gemini CLI 中用 gVisor 容器实现了动态沙箱，Plan Mode 现已默认用于复杂任务。沙箱配置文件根据 agent 的执行计划动态适配，而非应用静态安全策略。

### 静态 vs. 动态沙箱配置文件

标准 agent 沙箱应用固定安全配置文件：agent 可以访问这些目录、这些网络端点、这些系统调用，其他一律禁止。配置文件在部署时定义，执行期间不变化。

问题：固定配置文件必须在两个极端之间取舍——要么太宽松（授予 agent 任何任务都可能需要的一切），要么太严格（阻止某些任务合法需要的操作）。太宽松制造攻击面。太严格导致任务失败。

Gemini CLI 的做法：agent 进入 Plan Mode 时，先生成任务计划再执行。沙箱配置文件从计划中计算。如果计划说"读取 src/ 中的文件、修改 tests/、运行 pytest"，沙箱授予 `src/`（只读）和 `tests/`（读写）文件系统访问、授予 PyPI 网络访问（安装依赖），其他全部阻止。如果计划说"部署到预发环境"，沙箱授予预发环境 API 端点的网络访问。

### 为什么这事很难做对

动态沙箱有一个显而易见的漏洞：agent 生成计划，计划决定自己的权限。被入侵或被操纵的 agent 可以生成请求过度权限的计划。防御需要沙箱配置文件由策略引擎验证，限制任何计划可以请求的内容——无论 agent 推理如何。

Gemini CLI 实现为两阶段检查：计划的请求权限对照用户配置的最大权限封套验证，任何超出封套的权限请求触发人工审批提示。**Agent 无法在未经人工同意的情况下提升自身权限。**

这是最小权限原则在非确定性 agent 场景下的适配：agent 声明自己需要什么，系统验证它被允许什么，人决定边缘情况。这不是完美方案——基于计划的权限推断仍然可以被玩弄——但相比静态配置文件，是有意义的改进。

## 这些事情的共同点

一个模式：agent 模型能力大致趋同。所有前沿模型都能写代码、推理、使用工具、规划多步骤任务。差异化正在转向基础设施——agent 如何连接工具（MCP 无状态传输）、如何互操作（A2A 协议）、如何被评测（轨迹分析）、如何被沙箱化（动态配置文件）。

2026 年 4 月的这些进展都是基础设施决策。它们要填平的是"demo 里能跑的 agent"和"部署后能用的 agent"之间的鸿沟。模型写代码。基础设施决定那段代码是否能安全上线。
