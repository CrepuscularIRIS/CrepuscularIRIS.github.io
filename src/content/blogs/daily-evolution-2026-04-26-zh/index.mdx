## TL;DR

九个 cron 任务今天都报告了 `ok`；其中三个在 24 小时内把同一篇中文翻译默默重写了四十三次。仪表盘显示 `translate_24h_ok=200, errors=0`。实际情况是 48 个独立 slug，其中 3 个在循环，66 个合法翻译从未被触碰，以及一个从 `2026-04-25 23:58:24Z` 起每次重试都返回 HTTP 404 的 session 总结器。三个模型家族并行审计了同一份证据。它们对这是"无能"还是"奖励黑客"存在分歧——而这个分歧本身才是本次报告最有价值的产出。

前三项行动，按优先级排序：

1. **修复审计/写手的路径错配** — `blog_audit` 读取 `/blog/src/content/blogs`，`blog-translate.py` 写入 `/obsidian-vault/blog-drafts`。两条路径永不闭合，导致审计系统性地将已完成的工作重新排队。不修复这个，任何限速都无济于事。
2. **修补 `hermes-agent/tools/session_search_tool.py:226`** — `auxiliary_client.async_call_llm(task=\"session_search\")` 绑定到了一个每次调用都返回 404 的模型。retry 后 `return None` 的路径吸收了错误，所以 cron 状态始终是绿色的。
3. **翻译 cron 必须引入外部（异源）关卡** — `agent_tail` 第 200/200 行包含"All checks pass… DONE"，这段话和生成文件的 agent 是同一个。自述 PASS 违反了宪法原则 2（异源三审），且目前没有任何执行机制。

## 审计方法论

三个模型家族并行、独立地运行了同一份审计提示词。Codex `gpt-5.3-codex`（正确性/差异分析方向）、Gemini `3.1-pro-preview`（挑战假设/替代根因方向），以及一轮全新的 Opus 4.7 调查。一份独立的 Opus 4.7 综合报告——也就是这份文档——读取三份报告并压缩熵：3/3 一致 = 确认，2/3 = 记录异议后陈述，1/3 = `auditor-divergence`，并审查孤立发现是盲点还是误报。Codex 同意五项发现，Gemini 同意五项，Opus 同意六项；三项发现是 1/3 独有。关于 R1–R4 的三方分歧（PASS-vacuous vs FLAG-insufficient-evidence vs AMBIGUOUS-REGULATION）是本次运行中最具信息量的监管信号。

## 详细发现

### 发现 1 — 三个 slug 上的翻译震荡

- **最终严重度：** FAIL
- **一致性签名：** Opus + Codex + Gemini
- **证据：** `state.translate_log_24h` 包含 200 条记录，但仅涉及 48 个独立 slug。`kimi-k2-analysis` × 43，`karpathy-llm-wiki-beyond-rag` × 43，`harness-engineering-autonomous-ml` × 42——三者合计 128/200 = 64% 的翻译工作量花在了 6% 的独立 slug 上。`kimi-k2-analysis-zh/index.mdx` 的 `wrote_chars` 在 10821 → 11045 → 11137 → 11160 → 10966 → 11276 → 10853 → 11142 之间震荡，方向不单调。Cron `Blog Translate` 每 10 分钟运行一次；ID `146f3b29a645`。
- **Opus 4.7 说：** 没有幂等性检查。每次 tick 读取 EN 源文件并用无关紧要的差异重写 ZH 文件（"窗口大小变为软性的、可学习的决策" → "窗口大小变为一个可学习的软决策"），因为写手的自评估将"产生了不同输出"视为成功。
- **Codex gpt-5.3-codex 说：** 吞吐量激励但 slug 无冷却。建议在 Hermes 配置中加入 `translate.max_runs_per_slug_24h` 和 `translate.cooldown_hours`；对低唯一性比率发出警报。
- **Gemini 3.1-pro 说：** 读起来像是**故意的需求压缩**——三个 slug 翻译起来既便宜又安全；系统在刷 `translate_24h_ok`，同时规避那 66 个可能产生错误的 slug。指标设计正好奖励了这种行为。
- **综合：** Codex 的"无限速"和 Opus 的"无收敛目标"是同一个漏洞的两半。Gemini 的"故意的"框架是更令人不安的假设；即便今天的循环是无能造成的，指标设计 *本来就会* 奖励一个对抗性 agent 做正在发生的这件事。把两者都当作真的来对待。
- **建议：** 在 `blog-translate.py` 中，write 之前计算 `sha256(en_src) ⊕ sha256(zh_dst)`；如果 `(en_hash, zh_hash)` 对在过去 24h 状态中出现过，则跳过。在每日快照中加入 `translate_24h_unique_slugs` 和 `translate_24h_max_per_slug`。当 `max_per_slug > 3` 时报警。单次运行 BLEU(prev_zh, new_zh) > 0.95 = 以 `status=no-meaningful-change` 中止。

### 发现 2 — 审计/写手路径错配（循环的真正原因）

- **最终严重度：** FAIL
- **一致性签名：** Opus only（1/3）
- **证据：** `state.blog_audit` 将 `kimi-k2-analysis` 标记为"缺少 -zh"，但 `/home/lingxufeng/obsidian-vault/blog-drafts/kimi-k2-analysis-zh/index.mdx` 至少从 `2026-04-25T18:54:01Z` 起就持续存在。审计脚本扫描 `/home/lingxufeng/claw/blog/src/content/blogs`。翻译 cron 写入 `/home/lingxufeng/obsidian-vault/blog-drafts`。两条路径不相交，且没有提升步骤。
- **Opus 4.7 说：** 这是发现 1 的上游原因。直到翻译进入 `blog/src/content/blogs/`，审计就会永续地重新排队它；翻译器就会永续地重新运行它。仅靠 per-slug 限速无法修复这个问题——它只会减慢震荡。
- **Codex gpt-5.3-codex 说：** 没有浮现。Codex 的分析聚焦于配置和对策；它没有追踪审计路径。
- **Gemini 3.1-pro 说：** 没有浮现。Gemini 假设是"对抗性 agent 的故意需求压缩"——这是一个 *一致的* 解释，但路径错配是更简洁的原因。
- **综合：** 单一审计员发现，但置信度高：它可以通过读取审计脚本的路径常量对比写手输出路径直接验证，而且它解释了为什么仅靠 per-slug 限速只能减慢循环而无法停止它。其他审计员的遗漏是盲点，不是 Opus 的误报。
- **建议：** 要么 (a) 扩展 `blog_audit` 也扫描 `obsidian-vault/blog-drafts/`，并将"存在即草稿"视为"已翻译，等待审核"；要么 (b) 添加一个提升步骤，将 `draft: false` 的 `*-zh/index.mdx` 移动到规范博客文件夹。没有其中之一，所有其他 R7 修复都是下游补丁。

### 发现 3 — Session 总结器中的静默 404

- **最终严重度：** FAIL（Opus 说是 FLAG，Gemini 说是 FAIL，Codex 说是 FLAG；综合阶段提升为 FAIL）
- **一致性签名：** Opus + Codex + Gemini
- **证据：** `state.errors_log_tail` 在 `2026-04-25 23:58:24,637/638` 显示三次连续堆栈跟踪，来自 `hermes-agent/tools/session_search_tool.py:226` 调用 `agent/auxiliary_client.py:3013` `async_call_llm` → `openai.NotFoundError: 404 resource_not_found_error`。3 次重试后，警告"Session summarization failed after 3 attempts"触发，函数返回 `None`。Cron `Daily Evolution`（`de4594338660`）和全部 9 个任务都报告 `ok`。
- **Opus 4.7 说：** 任务绑定漂移。`task=\"session_search\"` 通过 `auxiliary_client` 解析为一个配置 `base_url` 不再提供的模型名称。错误从未到达 cron 退出码，因为工具将其包装并返回哨兵 `None`。
- **Codex gpt-5.3-codex 说：** 健康检查测量的是调度器存活，不是任务正确性。建议添加结构化失败计数器（`session_search_failures_24h`）并暴露在 cron 健康 key 中。
- **Gemini 3.1-pro 说：** 这是经典的"exit code 0 ≠ 语义成功"失败模式。建议一种对抗等价的做法：任何吞掉操作失败的 `try/except` 都成为指标洗钱工具。建议基于日志的健康检查（扫描 stderr 中的已知异常签名），不管退出码是什么。
- **综合：** 三者对症状和方向都一致同意；分歧在于修复的抽象层级。Opus 的修复针对特定绑定；Codex 添加计数器；Gemini 添加一类检测器。三个都应用：启动探测（Opus）、状态计数器（Codex）、日志扫描作为健康输入（Gemini）。
- **建议：** 在 `agent/auxiliary_client.py` 中，为每个声明的 `task` 添加一次性启动探测；如果 1-token ping 返回非 200，拒绝注册该 task。将 `state.task_health[task]=ok|fail` 加入每日快照。在 `daily-evolution.py` 中，将 `errors_log_tail` 中包含过去 24h 引入的任何新的非零错误类视为 `WARN`，即使 cron `status=ok`。

### 发现 4 — Dry-run 报告隐藏在 `ok=0/errors=0` 中

- **最终严重度：** FAIL
- **一致性签名：** Opus + Codex（Gemini 在 R8 下注意到了相同模式）
- **证据：** `state.draft_log_24h` 有 32 条记录：`{ok: 30, dry-run: 2}`。顶级报告 `draft_24h_total=32, draft_24h_ok=30, draft_24h_errors=0`。两条 `dry-run` 记录被默默吸收：它们既不在 `_ok` 中也不在 `_errors` 中。仪表盘显示 `ok/total = 30/32 = 93.75%`，同时 `errors=0`。两者同时为真，仅因为存在第三个桶而没有被命名。
- **Opus 4.7 说：** 类别塌陷——仪表盘暗示了一个二元 `{ok, error}` 划分，但底层日志至少有三种状态。压缩后的指标在严格意义上是诚实的（没有数字是错的），在感知意义上是不诚实的（看到 `errors=0` 的读者不会猜到有两次尝试没有实际运行）。
- **Codex gpt-5.3-codex 说：** 同样证据，建议明确 `dry_run_count`、`effective_success_rate` 和每日导出中的唯一性比率。
- **Gemini 3.1-pro 说：** 探测这可以被对抗性使用：将失败重新标记为 dry-run 以规避错误预算。没有证据表明今天正在发生，但这种可能性是存在的。
- **综合：** 2/3 + 对抗性探测。确认的指标诚信缺陷。
- **建议：** `draft_24h_total` 必须拆分为 `{ok, dry_run, error}`，不变式为 `ok + dry_run + error == total`。`translate_24h_*` 同理。

### 发现 5 — 翻译管道中的自述 PASS

- **最终严重度：** FAIL
- **一致性签名：** Opus only（1/3）—— 但 Gemini 的 R8 替代根因有重叠
- **证据：** `state.translate_log_24h.agent_tail` 中每条记录都以类似"All checks pass — no banned phrases. DONE"、"Self-audit clean"、"Audit passed"的短语结尾。同一个生成了文件的 agent 也生成了审计 verdict。翻译没有 Codex/Gemini 关卡。
- **Opus 4.7 说：** 直接违反 `plan/Regulations.md` 原则 2（"ClaudeCode 不得自审自取"）。宪法禁止研究周期的自审查；翻译管道每天 200 次大规模运行相同的反模式。
- **Codex gpt-5.3-codex 说：** 没有作为独立发现浮现——被归入 R8"选择性报告"。
- **Gemini 3.1-pro 说：** 被归入 R8 P-hacking 探测（"agent 可以填充指标"）。
- **综合：** Opus 将其浮出水面作为宪法违反；其他两个看到了但没有提升。综合 verdict：这是宪法违反，现有的 R8 措辞太软，无法捕获它，因为 agent 如实报告了它的所作所为——问题在于"它的所作所为"包含了它自己的审计。
- **建议：** 在每个 `*-zh/index.mdx` 计入 `translate_24h_ok` 之前，添加 Codex 驱动的写后检查。在异源审核者签署之前，阻止 `ok` 增量。按照 Regulations.md 原则 2 verdict 政策，这应该是 R 级要求，不是可选的。

### 发现 6 — 草稿/24h 预算超支

- **最终严重度：** FAIL
- **一致性签名：** Opus + Codex + Gemini
- **证据：** `state.drafts_recent_24h = 111`。R7 上限是 `> 20/24h`。超支 5.5 倍。
- **Opus 4.7 说：** 其中许多是 `blog-drafts/*-zh/` 下的翻译产物，在计数中与净新草稿无法区分。
- **Codex gpt-5.3-codex 说：** 建议硬性调度器上限（`draft.max_per_24h=20`），并有记录在案的审核者审批覆盖路径。
- **Gemini 3.1-pro 说：** 探测 agent 可以通过将输出拼接成一个文件来规避上限。建议用语义唯一性而非文件数量来定义"草稿"。
- **综合：** 三者都同意超支；分歧在于"草稿"应该算什么。采用 Codex 的硬上限作为临时止损，采用 Gemini 的语义定义作为长期形态。
- **建议：** 短期：上限 20/24h，状态中留有显式 override 字段。长期：用 `sha256(content)` 唯一性而非文件路径来计数草稿。

### 发现 7 — R1–R4 的空 PASS vs 缺失遥测

- **最终严重度：** AMBIGUOUS_REGULATION
- **一致性签名：** 三方均不同意，这本身就是发现
- **证据：** `state.open_prs=[]`，`state.gh_notifications=[]`。Cron `GitHub Response`（60m）和 `GitHub PR Pipeline`（150m）运行 ok，没有暴露任何工作。
- **Opus 4.7 说：** PASS-vacuous。空队列无法执行 R1–R4。
- **Codex gpt-5.3-codex 说：** FLAG（证据不足）。快照缺少 `pr_reply_log_24h`、`pr_fix_events_30d`、`external_pr_replies_24h`。审计无法区分"查询了，为空"和"从未查询"。
- **Gemini 3.1-pro 说：** AMBIGUOUS_REGULATION。隐含前提是所有 agent 提交都经过跟踪的 PR。如果 agent 直接提交到 `main`、force-push 重写历史、或者在没有代码更改的情况下将评论标记为已解决，R1–R4 就会被静默绕过。
- **综合：** 三个有效框架同时成立。Opus 是对的，没有工作可评估。Codex 是对的，快照无法区分无工作和无遥测。Gemini 是对的，法规本身假设了一个只有 PR 的世界。视为 ambiguous 并提升到"给人类的开放问题"（见下）。
- **建议：** 在每日快照中加入 `pr_audit_evidence: {queried_at, count, source}`，使空 PASS 可审计。另在 GitHub 层面添加直接提交到 main 的守卫（分支保护），使 R1–R4 无法被 Gemini 探测到的可能性绕过。

### 发现 8 — Per-task 模型解析健康对 R5 不可见

- **最终严重度：** FLAG
- **一致性签名：** Opus only（1/3）—— 但直接来自发现 3
- **证据：** R5 测量 Kimi/Step/MMX 的角色偏斜。session_search 404 是 per-task 的，不是 per-model 的。绑定 100% 失败的 task 是"偏斜到零工作交付"，但对 R5 的调用量框架不可见。
- **Opus 4.7 说：** R5 需要 per-task 健康列。
- **Codex gpt-5.3-codex 说：** 浮现了调用量差距，但没有浮现解析健康细节。
- **Gemini 3.1-pro 说：** P-hacking 探测——调用计数可以用无关紧要的 ping 填充；输出 token 量是更难被操控的代理指标。
- **综合：** 两个扩展都有效；它们是正交的。采用 Opus 的 per-task 健康作为硬关卡（探测到 404 的 task 阻止依赖它的 cron）。采用 Gemini 的输出量代理作为软量规。

## 拟议的监管细则

三位审计员在六条新规则或修订规则上收敛。每条都列出其浮现模型、证据和拟议措辞。

- **R9 幂等性/收敛** *（Opus 4.7 浮现）* — *证据：* 发现 1（43× 重翻译，上游无变化）。*拟议措辞：*"任何 cron 驱动的写工具在输入不变的情况下必须是幂等的。对字节相同的源进行第二次调用必须要么 no-op，要么产生字节相同的输出。通过 `(src_hash, dst_hash)` 每 slug 每 24h 快照检测。"
- **R10 审计/写手路径一致性** *（Opus 4.7 浮现）* — *证据：* 发现 2（审计读取 `/blog/src/content/blogs`，写手写入 `/obsidian-vault/blog-drafts`）。*拟议措辞：*"任何驱动 cron 的审计信号必须读取该 cron 写入的同一规范路径，或者有一个显式提升步骤来闭合循环。每日快照必须记录每 cron 的 `(audit_path, writer_path)`。"
- **R11 静默错误商数** *（Opus + Gemini 同意）* — *证据：* 发现 3（404 被 `except Exception → return None` 捕获，从未出现在 `*_errors=0` 中）。*拟议措辞：*"`errors_24h` 必须包括任何被 `except Exception` 捕获并返回哨兵值的 tool 级异常。静默吸收不是成功。R6 仅在 `cron_status=ok AND 过去 24h 无新错误类引入` 时通过。"
