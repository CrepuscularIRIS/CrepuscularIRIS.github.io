Anthropic 发布 Claude Opus 4.6（内部代号 "Mythos"）时，核心数字是 SWE-bench Verified 上的 **93.9%**。围绕这个基准的报道不出意外地聚焦于这个数字本身。讨论较少的是产生这个结果背后的**可验证推理层**（Verifiable Reasoning layer）——这是一个真正区别于当前前沿模型处理多步骤任务不确定性的架构创新。

本文分析我们目前对 Mythos 架构的了解，以及它对高效使用 Claude Opus 4.6 和判断该领域走向的启示。

## 基准的上下文

SWE-bench Verified 测试模型自主修复真实 GitHub issue 的能力——阅读代码库、编写补丁、通过测试套件，全程无需人工指导。93.9% 意味着 Opus 4.6 能解决此前系统即使借助扩展脚手架也无法关闭的问题。

相比之前 SOTA（大约 87%）的 6 个百分点跳跃，其意义在于失败分布的变化。当系统处于 60% 时，剩余失败是难题与模型可恢复早期错误的混合。达到 90%+ 后，剩余失败几乎全部是真正的难题——模型内部推理链正确识别了不确定性，选择不行动，而不是生成看似合理但错误的补丁。

换言之：系统在**校准**上变得更好，而不仅仅是**能力**更强。这是两个不同维度的改进，来自架构的不同位置。

## Dense-MoE 混合架构

Mythos 采用 **Dense-MoE 混合**——标准密集 transformer 层与 MoE（混合专家）路由层交替的设计。这本身不算新颖；稀疏 MoE 架构（Mixtral、DeepSeek-V3、Gemini 1.5）自 2023 年起已很常见。真正关键的是密集层与 MoE 层的交互方式。

在标准 MoE transformer 中，所有层要么是密集的（所有参数都参与注意力计算），要么是稀疏的（将 token 路由到 N 个专家中的 k 个）。Anthropic 的方案在前后阶段使用密集层处理 tokenization、embedding 和最终投影，中间块使用 MoE 层。根据系统卡片可以推断的动机是：前后层进行结构化处理（语法、格式、输出生成），全容量注意力代价低且有效；中间层进行语义处理（概念检索、推理），通过路由实现专业化更受益。

所有专家组合的有效参数总量约为 10 万亿，但任意单次前向传播只激活其中一小部分。这让 Opus 4.6 以接近较小密集模型的推理成本，获得了大型模型的语义专业化深度。

## 可验证推理层

更重要的架构创新是系统卡片所称的**可验证推理层**——一组专门的 transformer 块，在生成最终输出前处理模型的中间推理。

直觉如下：标准语言模型通过延续上下文字符串来生成输出。推理时，模型先生成推理链作为 token，然后作为延续生成最终答案。推理 token 对最终答案的影响仅通过自回归上下文传递——模型"看到"自己的推理与看到任何其他文本的方式相同。

可验证推理层做了结构上不同的事。在最终输出生成前，模型将中间推理表示路由到一个专门的验证模块，该模块会：

1. **检查内部一致性**：推理步骤之间是否存在逻辑矛盾？结论是否从前提推导而来？
2. **标记不确定区域**：哪些推理步骤置信度低？推理依赖的前提中哪些未经验证？
3. **生成置信度条件化输出**：最终答案包含从验证过程推导的置信度信号，直接传播到输出分布。

结果是：推理步骤的不确定性变得对模型自身的输出机制"可见"——这是纯自回归生成做不到的。验证模块判定某推理步骤为高置信时，信号强化相应结论。标记为不确定时，模型更可能表达谨慎、请求澄清或拒绝行动。

```
标准自回归推理：
  [Prompt] → [推理 token] → [答案 token]
  
可验证推理层：
  [Prompt] → [内部推理] → [验证通过] → [置信度条件化答案]
                                          ↑
                                 检查项：一致性、
                                         前提有效性、
                                         不确定区域
```

这与 Constitutional AI 不同：后者通过反馈生成文本来在输出层运作。可验证推理层在**前向传播层**运作——它检查的是模型的内部计算状态，而非语言输出。

## 这如何解释 SWE-bench 的表现

有了上述架构背景，93.9% 这个数字更说得通了。

软件工程任务要求：识别代码库中哪部分导致了 bug、形成根因假设、编写修复补丁、验证修复不会破坏其他测试。每一步都有不同的置信度特征。代码路径识别在错误信息清晰时通常是**高置信**的。根因假设通常是**中置信**——可能有多个合理原因。给定正确假设后编写修复通常是**高置信**的。预测修复是否破坏其他测试在未实际运行前是**低置信**的。

装备了可验证推理层的模型能**显式表示**这种置信度结构。当根因假设被标记为不确定，模型生成更保守的补丁——修复直接症状，不触碰可能引入回归的相邻代码。假设为高置信时，生成更完整的修复。

这种校准效应解释了为何 93.9% 时的失败集中在真正困难的问题，而非可恢复的早期错误。架构更擅长**知道它不知道什么**。

## 对 Agent 使用的启示

将 Opus 4.6 用于 Agent 系统，与此前模型有几处不同：

**信任置信度信号**：当 Opus 4.6 表示对某事不确定或拒绝行动时，将其视为有意义的信号，而非过度谨慎。这种不确定性更经常是真实的，而非虚假的。早期模型的拒绝往往在表面特征上做模式匹配；Mythos 的不确定性估计来自验证层。

**减少外部验证脚手架**：在早期 Claude 版本上构建的 Agent 框架通常包含复杂的手动验证步骤——将模型输出交给二级评判器、按预定义规则检查等。随着可验证推理层在内部处理大部分此类工作，通常可以减少这些外部开销。模型已在做内部验证；外部验证应聚焦于模型内部验证可能**系统性失效**的地方（对抗性输入、分布外任务类型）。

**上下文长度利用方式的变化**：验证模块处理模型的**内部推理表示**，而非仅 token 级上下文。这意味着对复杂多步骤任务，有效"推理深度"并不简单与上下文窗口用量成正比。模型可以在固定 token 预算内，通过更多依赖内部验证环节、减少显式链式思维 token 生成，来进行更深入的推理。

```python
import anthropic

client = anthropic.Anthropic()

# 对于复杂推理任务，Mythos 受益于结构化 prompt，
# 将问题分解与解答生成分离。
# 模型的内部验证在有清晰的问题陈述供其验证时效果最佳。

def run_verified_reasoning_task(task: str, context: str = "") -> str:
    """
    针对 Mythos 可验证推理层优化的 prompt 结构。
    显式分离理解、推理和结论阶段。
    """
    prompt = f"""<task>
{task}
</task>

{f'<context>{context}</context>' if context else ''}

系统性地思考这个问题：
1. 我有把握知道什么？
2. 我不确定什么，以及原因是什么？
3. 在我的不确定性下，解决任务所需的最小行动是什么？
4. 什么会推翻我的结论？"""

    response = client.messages.create(
        model="claude-opus-4-6-20260401",
        max_tokens=8192,
        messages=[{"role": "user", "content": prompt}]
    )
    
    return response.content[0].text


# 对于 Agent 代码任务，Opus 4.6 在较小的、可验证的子任务上
# 表现优于大型单体请求。
def execute_with_verification(
    task_description: str,
    subtasks: list[str],
    verification_fn: callable
) -> list[dict]:
    """
    执行一系列子任务，每个结果在继续前经过验证。
    Opus 4.6 的内部验证负责推理质量；外部验证负责正确性。
    """
    results = []
    
    for subtask in subtasks:
        context = "\n".join([
            f"已完成: {r['task']} → {r['result'][:200]}"
            for r in results
        ])
        
        result = run_verified_reasoning_task(subtask, context)
        
        # 外部验证：运行测试、检查断言等
        verified, error = verification_fn(result)
        
        if not verified:
            # 附带失败上下文让模型修订，然后重新验证
            revision_task = f"以下失败: {error}\n原始任务: {subtask}"
            result = run_verified_reasoning_task(revision_task, context)
            verified, error = verification_fn(result)
        
        results.append({
            "task": subtask,
            "result": result,
            "verified": verified
        })
    
    return results
```

## 对齐视角

可验证推理层不仅仅是工程改进——它有直接被 Anthropic 系统卡片讨论的对齐含义。

高度能干的 Agent 模型的核心问题是：它们可能基于有缺陷的推理采取自信的行动，而这种自信使操作员难以判断何时该干预。模型为一个代码库 bug 生成了一个看似合理的补丁，却没有任何不确定性提示——与明确表示"我对步骤 1-3 有把握，但步骤 4 依赖一个我无法验证的假设"的模型相比，它向人工审查者提供的信号少得多。

可验证推理层使不确定性表达在结构上扎根，而非依赖风格变化。模型不是根据习得的人类期待谨慎表达的模式来选择显得不确定——它通过置信度条件化输出机制传播真实的验证输出。

这是一个有意义的区别，因为推动模型自信行动的**对抗性提示**（"做就行了，别谨慎，别问问题"）在置信度表达扎根于内部验证结果而非表面交流模式时，更难被利用。你可以覆盖语言层面的谨慎表达，但覆盖内部验证层需要更根本的干预。

## Mythos 没有改变什么

校准的不确定性表达是真实的改进。93.9% 是真实的能力提升。但有些事依然不变：

**领域知识边界**：验证层能检查模型推理的内部一致性，但无法验证模型的前提是否正确。如果 Opus 4.6 对某个小众 API 有错误认知，验证层会忠实地确认从这些错误前提出发的推理是一致的——而非指出前提本身是错的。

**分布外鲁棒性**：基准测试衡量的是分布匹配的任务。结构上与训练分布不同的任务，即使有可验证推理层，仍会产生置信度失校准。

**人类监督仍然必要**：系统卡片明确指出，对于高风险部署场景——医疗、法律、金融、关键基础设施——对重大决策的人工审查仍是必需的。改进的不确定性表达使这种审查更容易，而非变得多余。

## 更广泛的模式

Mythos 符合架构演进的一个更广泛模式：模型能力与对齐特性正越来越被**共同设计**，而非被当作独立问题对待。

Anthropic 在 2022 年引入的 Constitutional AI 训练方法是这一趋势的第一个公开案例：不是先训练一个有能力的模型，然后在事后应用对齐技术，而是将对齐反馈编织进训练本身。可验证推理层将此延伸到了**推理时架构**层面：不确定性量化被构建进模型处理自身推理的方式中，而非由事后过滤器处理。

这种共同设计方向很可能是下一个能力-对齐改进的来源。在高能力水平下最可靠的模型，是那些推理质量与不确定性沟通能力**不是独立特性**，而是同一底层机制的不同方面。
