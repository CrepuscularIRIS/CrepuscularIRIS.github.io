二次注意力复杂度是陈年旧事了。Longformer 给出了局部窗口加全局 token 的方案。BigBird 混合了滑动窗口、随机注意力和全局 token。Linformer 将键值投影到更低秩的空间。这些方法都在可扩展性和能力之间做了取舍，但没有一个真正逃脱了手工设计稀疏模式的老路。

Moonshot AI 的 MoBA（Mixture of Block Attention，arXiv:2502.13189）走了一条不同的路：让模型自己决定关注上下文的哪些部分，使用的是让混合专家（MoE）生效的同一套路由逻辑——但这次应用的对象是注意力分块而非 FFN 专家。没有可训练的路由参数。没有固定的稀疏模式。只有对分块平均键向量做 top-k 选择的操作。

结果是：论文发布当天，MoBA 就已经部署到了 Kimi 的生产环境；线上服务能处理 200K+ token 的输入；在 32K 序列长度下实现最高 **40 倍**的加速。

## 为什么固定稀疏模式会失效

Longformer 的直觉是成立的：长文档中大多数 token 只需要关注附近的上下文，只有少数特殊 token 需要全局视野。但"大多数 token"和"附近上下文"只是近似。在实际场景中，一个给定查询的相关上下文可能是 50,000 token 之前的一个段落，或者是不同章节中合同里的某个条款。

固定模式无法建模这种情况。如果相关的 KV 分块不在局部窗口或全局 token 集合中，它对这个注意力头就是不可见的——从那个位置的角度看，信息永久丢失了。这就是为什么 Longformer 和 BigBird 在需要长距离检索的任务上，尽管效率不错，但表现往往不如全注意力——稀疏模式不知道重要的东西在哪里。

正确的修复方案是**数据驱动的稀疏**：让每个查询根据查询本身的内容，动态选择要关注哪些键值分块。这就是 MoBA 的核心思想。

## MoBA 架构

一旦看透了 MoE 的类比，架构就很简单了。

在标准 MoE 层中，输入是一个 token 嵌入，路由器用学到的线性投影计算 N 个专家的得分，然后激活 top-k。每个专家是一个独立的 FFN。Token 只流经它被分配的 k 个专家。

在 MoBA 中，输入是一个查询向量，"路由器"计算 M 个 KV 上下文分块的得分，然后激活 top-k。每个分块是一段连续的键值对。查询只关注它被分配的 k 个分块。

```
标准全注意力：
  Q: (N, d)
  K, V: (N, d)
  Output: Attention(Q, K, V)  —  O(N²) 计算量

MoBA 稀疏注意力：
  Q: (N, d)
  K, V: (N, d) → 切分为 M 个分块，每个分块大小 B = N/M

  对每个查询 q_i：
    score_j = q_i · mean(K_block_j)   # 每个分块一个标量得分，j=1..M
    selected = argtop_k(scores)        # 选出 k 个分块
    output_i = Attention(q_i, K[selected], V[selected])

  总体复杂度：O(N · k · B) ≈ O(N)，当 k, B << N 时
```

关键设计决策是**无参数门控**：MoBA 不使用学到的独立路由网络（线性层 + M 个专家上的 softmax），而是使用查询与每个分块的平均键向量的点积。这是一个自然的相关性度量——如果一个分块的平均键在嵌入空间中与查询接近，这个分块很可能包含相关上下文。

这绕过了学习型 MoE 路由器的主要失败模式：**路由崩溃**（routing collapse）——路由器持续将所有 token 分配给少数热门专家，导致其余专家训练不足。由于 MoBA 的门控没有可训练参数，因此没有什么可以崩溃。

## 实现：朴素版 vs 高效版

开源仓库（github.com/MoonshotAI/MoBA）提供了两种实现，值得在不同层次上理解：

### 朴素实现（研究用途）

朴素版本构建一个稀疏注意力掩码并送入 FlashAttention。它可读且正确：

```python
import torch
import torch.nn.functional as F
from einops import rearrange

def moba_naive(
    q: torch.Tensor,           # (batch, heads, seq_len, d_head)
    k: torch.Tensor,           # (batch, heads, seq_len, d_head)
    v: torch.Tensor,           # (batch, heads, seq_len, d_head)
    num_blocks: int,           # M: KV 分块数量
    top_k: int,                # k: 每个查询要关注的分块数
) -> torch.Tensor:
    B, H, N, D = q.shape
    block_size = N // num_blocks
    
    # 将键重组为分块，计算每个分块的平均键向量
    # k_blocks: (B, H, M, block_size, D)
    k_blocks = rearrange(k, 'b h (m bs) d -> b h m bs d', m=num_blocks, bs=block_size)
    # mean_keys: (B, H, M, D)
    mean_keys = k_blocks.mean(dim=3)
    
    # 对每个查询与每个分块的平均键进行评分
    # q: (B, H, N, D), mean_keys: (B, H, M, D)
    # scores: (B, H, N, M)
    scores = torch.einsum('bhnd,bhmd->bhnm', q, mean_keys)
    
    # Top-k 分块选择（每个查询独立）
    # topk_indices: (B, H, N, k)
    _, topk_indices = scores.topk(top_k, dim=-1)
    
    # 构建布尔掩码：(B, H, N, N)
    # 查询 i 可以关注位置 j，当且仅当 j 所在的分块在 topk_indices[i] 中
    mask = torch.zeros(B, H, N, N, dtype=torch.bool, device=q.device)
    for block_idx in range(num_blocks):
        block_start = block_idx * block_size
        block_end = block_start + block_size
        # 哪些查询选了这个分块？
        selected = (topk_indices == block_idx).any(dim=-1)  # (B, H, N)
        mask[:, :, :, block_start:block_end] |= selected.unsqueeze(-1)
    
    # 用稀疏掩码进行标准注意力计算
    scale = D ** -0.5
    attn = torch.einsum('bhnd,bhmd->bhnm', q * scale, k)
    attn = attn.masked_fill(~mask, float('-inf'))
    attn = F.softmax(attn, dim=-1)
    return torch.einsum('bhnm,bhmd->bhnd', attn, v)
```

这一步评分复杂度 O(N·M)，注意力计算复杂度 O(N·k·B)——当 `k·B << N` 时已经优于 O(N²)，但掩码构建的开销使它不适合生产环境。

### 高效实现（生产用途）

高效版本在 CUDA kernel 层面操作，完全跳过掩码构建。不构建密集的 N×N 掩码，而是直接 gather 选中的 KV 分块，然后在 gather 后的张量上运行 FlashAttention：

```python
# 高效 kernel 逻辑的伪代码
# （实际实现通过 flash-attn ≥ 2.6.3，CUDA 层面）

def moba_efficient_kernel(q, k, v, block_indices):
    """
    block_indices: (N, k) — 每个查询预先计算好的 top-k 分块索引
    
    不是掩码，而是直接 gather 选中的 KV tiles：
    """
    outputs = []
    for i, query in enumerate(q):  # 每个查询一个 (d_head,)
        selected_k = k[block_indices[i]]  # (k * block_size, d_head)
        selected_v = v[block_indices[i]]  # (k * block_size, d_head)
        # 在 gather 后的 k·B 个 token 上做 Flash Attention
        out_i = flash_attn(query.unsqueeze(0), selected_k, selected_v)
        outputs.append(out_i)
    return torch.stack(outputs)
```

论文中提到的 **40 倍加速**来自这个 kernel 在 32K 序列、top-k=3、2048 分块下的运行——每个查询只关注 3 × (32768/2048) = 48 个 token，而不是 32768 个。KV 缓存读取量减少约 **99.5%**，而由于内存带宽是长上下文推理的瓶颈，加速大致与此成正比。

## 超参数敏感性

论文的消融实验揭示了一个实用的配置指南：

```python
# 消融研究推荐的配置
configs = {
    "quality_first": {
        "num_blocks": 512,
        "top_k": 8,
        "block_size": "N/512",
        "use_case": "需要高召回的任务，如长文档问答"
    },
    "balanced": {
        "num_blocks": 2048,
        "top_k": 3,
        "block_size": "N/2048", 
        "use_case": "默认配置，与论文主要结果一致"
    },
    "throughput_first": {
        "num_blocks": 4096,
        "top_k": 3,
        "block_size": "N/4096",
        "use_case": "最大吞吐量，准确率小幅牺牲"
    }
}
```

消融实验中有三个发现值得特别指出：

**分块大小的影响比你想象的小。** B 从 16 到 64 token 变化时，对下游任务准确率的影响相对较小。路由质量（门控能否找到正确的分块？）压过分块粒度本身的影响。

**k=3 是拐点。** top-k 从 1 增到 3 带来较大的准确率收益；从 3 到 8 则边际递减。这与 MoE 文献中的发现一致：top-2 路由对 FFN 专家通常已经足够。

**逐层独立路由优于跨层共享路由。** 不同层学会了将查询路由到不同分块，说明每一层从长上下文中提取的是定性不同的信息。

## 全注意力 / 稀疏注意力切换

一个被低估的工程特性：只需在推理时改变 top-k，相同的模型权重就能在全注意力和 MoBA 稀疏注意力之间切换。

```python
class MoBALayer(nn.Module):
    def __init__(self, d_model, num_heads, num_blocks=2048, default_top_k=3):
        super().__init__()
        self.num_blocks = num_blocks
        self.default_top_k = default_top_k
        self.attn = MultiHeadAttention(d_model, num_heads)
    
    def forward(self, x, top_k=None, mode="sparse"):
        if mode == "full" or top_k is None and mode != "sparse":
            # 标准全注意力 — 等价于选择所有分块
            return self.attn(x)
        else:
            k = top_k or self.default_top_k
            return moba_efficient(x, x, x, self.num_blocks, k)

# 小批次精度校准：使用全注意力
model.set_mode("full")
calibration_output = model(calibration_batch)

# 200K token 输入的生产推理：使用 MoBA
model.set_mode("sparse", top_k=3)
production_output = model(long_context_input)
```

这个切换机制对生产部署很有价值：你可以在小输入上用全注意力验证模型正确性，然后无需维护两套模型权重就能以 MoBA 部署长上下文效率优化。

## MoBA 与竞争方案的对比

| 方法 | 稀疏类型 | 可训练路由器 | 复杂度 | 长距离召回 |
|------|---------|------------|--------|-----------|
| Longformer | 固定（窗口 + 全局） | 否 | O(N) | 受窗口大小限制 |
| BigBird | 固定（窗口 + 随机 + 全局） | 否 | O(N) | 更好，仍是固定 |
| MoE Attention | 学习路由 | 是 | O(N·k·B) | 数据驱动 |
| **MoBA** | **数据驱动，无参数** | **否** | **O(N·k·B)** | **数据驱动** |
| GQA/MQA | 全注意力，共享 KV | 否 | O(N²/H) | 完整 |

MoBA 的独特定位：数据驱动的稀疏，却没有学习路由器的训练不稳定性。在短序列上它不是最快方案（GQA 在那里胜出），但在 100K+ token 时它在效率/召回权衡上占据主导。

## 生产影响

MoBA 在论文发布当天就上线的生产环境，这不是脚注——而是证据：设计被部署现实所约束，而非仅仅是基准目标。

一种方法实现了 98% 的计算量削减，但如果需要改变架构从而破坏现有推理基础设施，对生产团队实际上没有帮助。MoBA 与 FlashAttention 的兼容性以及其"即插即用"的语义（与标准注意力接口相同，只需添加路由参数）使部署成为可能。

Moonshot AI 报告称 MoBA 的生产部署直接促成了 Kimi 线上服务 200K 上下文窗口的落地，而部署中积累的工程经验又影响了后续模型迭代。VMoBA（arXiv:2506.15465）是将同一路由原则适配到视频扩散模型的变体，将注意力扩展到 3D 时空维度——说明这套方法不只适用于文本。
