# ToolGen: 统一工具检索与生成的生成式范式

**作者：** Wang 等（Renxi Wang, Xudong Han, Lei Ji, Shu Wang, Timothy Baldwin, Haonan Li）  
**会议：** ICLR 2025 | **链接：** [OpenReview](https://openreview.net/forum?id=XLMAMmowdY)

---

## 一句话摘要

ToolGen 把「先检索再调用」的两段式流水线砍成一步：每个工具变成 LLM 词表里的一枚特殊 token，模型像生成普通文字一样直接生成工具调用。

---

## 为什么选这篇

当前绝大多数 tool-augmented LLM 都在做同一件事：把工具描述塞进 prompt，然后指望外部检索器挑对工具。ToolGen 问了一个更狠的问题：*如果模型本身就背下了所有工具呢？*

答案直白得近乎粗暴。通过继续预训练把工具知识 bake 进模型权重，ToolGen 直接取消了检索器。这不是边缘优化，而是**范式迁移**——从检索增强生成彻底转向参数化工具记忆。对需要同时调度成千上万个 API 的 agent 系统来说，光是省下的上下文长度就足以让人认真读这篇论文。

---

## 核心方法（3 分钟版）

传统 tool use 像一个必须先找书才能读书的图书管理员。LLM 收到 query，检索器扫描工具描述库，把 top-k 结果塞进 prompt。两个问题必然随之而来：上下文长度爆炸，检索延迟多出一个可能静默失败的流水线环节。

ToolGen 烧了图书馆，让模型直接背下每一本书。

**第一步——把工具空间 token 化。** 每个工具分配一枚专属特殊 token，工具的签名（名称、参数、行为模式）被编码进该 token 的表示向量。

**第二步—— bake 进权重。** LLM 在工具调用数据上继续预训练，像预测普通词汇一样预测工具 token，在内部建立起工具语义与参数结构的完整映射。

**第三步——端到端生成。** 推理时，模型把工具调用当作自然的 next-token 决策输出。没有检索步骤，没有上下文膨胀，没有外部索引。作者报告了在 **47,000+ 工具** 上的实验——这个规模下传统检索会被 prompt 长度直接掐死。

核心洞察在于：工具选择与参数生成被统一在同一个自回归目标下。模型不需要「决定调用工具」作为一个独立阶段；它只是生成概率最高的 token 序列，而这些序列中恰好包含工具调用。

---

## 关键结果

- **规模：** 在 **47,000+ 工具** 上评估——远超此前工作通常的几十到几百个工具。
- **性能：** 相比基于检索的基线取得有竞争力或更优的结果，但源材料未提供具体数值对比。
- **效率：** 彻底消除检索延迟与上下文长度开销。

## 局限与未回答的问题

- **源材料无具体数字。** 摘要提到「在 47,000+ 工具上的实验结果」后截断，未给出具体指标。没有完整论文无法判断增益是边际还是质变。
- **训练成本。** 在 47,000 个工具上继续预训练并不便宜。作者未讨论计算预算，也未说明小模型能否在不发生灾难性遗忘的前提下吸收如此规模的工具知识。
- **动态工具集。** 部署后若新增工具，需扩展词表并重新训练模型——更新周期比单纯重建检索索引要重得多。
- **未见工具的泛化。** 论文假设模型在训练时已见过所有工具。面对语义相似但全新的工具时表现如何，尚不明确。

## 延伸线索

- **Gorilla（Patil et al., 2023）** —— 相反哲学：训练检索器按需拉取 API 文档。对比 Gorilla 与 ToolGen 可以完整画出「参数化工具记忆 vs. 检索式工具记忆」的设计空间。
- **ToolLLM（Qin et al., 2023）** —— 大规模工具学习配合显式检索；理解 ToolGen 砍掉了什么，这篇基线很有用。
